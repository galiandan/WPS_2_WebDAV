# 从 Python 迁移到高性能实现

> 状态：规划文档，尚未开始迁移
>
> 目标：在不改变现有用户操作和接口行为的前提下，评估并逐步把高并发、文件流式传输和 WebDAV 服务从 Python 迁移到更适合长期运行的后端语言，同时将网页前端整理为独立的原生 HTML/CSS/JavaScript 文件。

## 1. 先说结论

推荐后端使用 **Go**，不推荐第一版使用 C++。

Go 更适合本项目的原因：

- 自带成熟的 HTTP、TLS、URL、并发和文件流 API；
- 可以编译成一个静态或近似静态的单文件程序，VPS 部署简单；
- goroutine 很适合同时处理 WebDAV 客户端、WPS 控制请求和对象存储流；
- 内存占用通常低于 Python 多线程进程，交叉编译和回滚也简单；
- 新贡献者更容易读懂和构建，长期维护成本低；
- 有可复用的 WebDAV 基础库，但核心协议边界仍可以由项目自己的测试控制。

C++ **完全可以实现**，但不适合作为当前项目的第一迁移目标。C++ 的运行性能没有问题，真正的风险在于 HTTP 解析、TLS、XML、断开连接、内存所有权、异常路径和第三方库版本组合。对一个需要公开部署的 WebDAV 服务来说，错误的资源生命周期或边界检查可能比 Python 的性能损失更危险。

如果未来有熟悉 C++ 网络服务、安全审计和构建系统的维护者，可以保留 C++ 方案；在当前“用户操作要简单、VPS 要容易部署、项目要适合开源贡献”的目标下，Go 的综合成本更低。

## 2. 是否真的需要迁移

Python 的主要问题不应只凭感觉判断。当前服务大部分时间在等待 WPS 或对象存储网络，CPU 并不一定是瓶颈。迁移前应记录以下指标：

- 同时连接数和活跃 WebDAV 请求数；
- `PROPFIND`、上传、下载、COPY 的延迟和吞吐；
- 进程常驻内存、峰值内存和临时磁盘使用量；
- WPS 上游请求数量、失败率和重试次数；
- 客户端断开后，上游流是否及时关闭；
- VPS 在 1.6 GiB 内存、无 Swap 条件下的稳定性。

如果瓶颈主要是 WPS 服务端延迟，换语言不会明显加快单个文件传输；迁移的主要收益会是更低的并发开销、更可预测的内存占用和更容易扩展的连接处理。性能测试结果应作为迁移记录的一部分，不能用未经测量的“语言快慢”替代基准。

## 3. 后端候选比较

| 语言 | 性能与并发 | 部署 | WebDAV/HTTP 生态 | 学习与维护成本 | 结论 |
| --- | --- | --- | --- | --- | --- |
| Go | 很好，网络 I/O 和流式传输简单 | 很好，单二进制 | 成熟，标准库基础强 | 低到中 | **首选** |
| Rust | 很好，内存安全和资源控制强 | 很好，可生成单二进制 | HTTP 生态成熟，WebDAV 需要更多自建适配 | 中到高 | 第二选择 |
| C++ | 很好，性能上限高 | 中等，依赖和 ABI 需管理 | 库很多但组合复杂 | 高 | 可行但不优先 |
| Java/Kotlin | 很好，生态成熟 | 中等，需要 JVM 和内存预算 | 成熟 | 中 | 不适合当前低配目标 |
| Node.js | 网络 I/O 好 | 简单但依赖较多 | HTTP 生态丰富 | 低到中 | 内存和长流场景不优先 |

本项目不应为了追求理论峰值而选择增加部署步骤、运行时依赖或维护难度的方案。

## 4. C++ 方案的具体评价

### 可以做什么

C++ 可以覆盖所有现有需求：

- HTTP/1.1、Basic Auth 和 WebDAV 方法；
- WPS JSON API 和签名对象存储请求；
- 上传、下载、单范围 `Range` 和 multipart 流；
- 连接取消、并发限制和内存/磁盘预算；
- 独立静态网页资源服务。

### 需要承担什么

若使用 C++，至少要固定并审计：

- HTTP 服务器库，例如 Boost.Beast、Drogon 或 Crow；
- TLS 库和证书验证策略；
- XML 解析器，必须关闭外部实体和危险扩展；
- JSON 库和 URL/路径编码规则；
- 构建工具链、系统库版本和静态链接策略；
- 每一条上传、下载、断开和异常路径的资源释放；
- ABI、编译器和发行版差异带来的安装问题。

不能把“使用 C++”等同于“自动更安全或更快”。如果没有持续的 AddressSanitizer、UndefinedBehaviorSanitizer、模糊测试、依赖漏洞扫描和多平台构建，C++ 迁移可能提高项目风险。

## 5. 前端重构目标

前端不需要 React、Vue 或浏览器扩展。目标结构是原生静态资源：

```text
web/
├── index.html    页面结构和可访问性标记
├── style.css     布局、颜色、响应式样式
└── app.js        目录浏览、上传、进度和操作逻辑
```

当前前端已经使用原生 DOM、Fetch、`XMLHttpRequest` 和 CSS 思路；迁移时主要是把嵌入在 Python 字符串中的资源拆出来，并保留以下行为：

- 根目录和多 WPS 空间文件夹显示；
- 面包屑、搜索、刷新和返回上级；
- 拖动到整个页面上传；
- 上传进度、实时速度、失败提示和取消状态；
- 新建文件夹、重命名、移动、删除和下载；
- WPS 连接状态的明确显示；
- 云盘显示名称设置；
- HTML 文本、属性和 JavaScript 数据的安全编码。

后端应把静态资源当作只读文件提供，禁止把用户输入拼进 HTML、脚本或响应头。前端仍然需要少量 JavaScript 才能完成上传和目录操作；“使用 HTML/CSS 绘制”不意味着要取消必要的交互脚本。

## 6. 目标后端结构（Go 方案）

```text
cmd/wps-adapter/main.go       启动参数和信号处理
internal/httpapi/              REST、Basic Auth 和状态码
internal/webdav/               WebDAV 方法、Depth、Range 和锁
internal/wps/                  WPS 控制 API、Cookie 和 refresh 流程
internal/storage/              路径解析、空间挂载和元数据缓存
internal/transfer/             上传、下载、multipart 和资源预算
web/                            index.html、style.css、app.js
cmd/wps-login/                 后续可选的登录同步工具
```

第一阶段可以继续保留现有 Python `wps_login.py`，只迁移 VPS 上长期运行的服务。登录助手不是性能热点，延后迁移能显著降低一次性变更范围。

## 7. 必须保持的接口契约

迁移不能改变普通用户看到的步骤，也不能悄悄改变现有客户端行为。以下内容应先写成跨语言协议测试：

- `/healthz`、`/api/v1/status`、`/api/v1/session/import`；
- REST 列表、元数据、上传、下载、文件夹、重命名、移动和删除；
- WebDAV `OPTIONS`、`PROPFIND`、`GET`、`HEAD`、`PUT`、`MKCOL`、`DELETE`、`MOVE`、`COPY`、`LOCK`、`UNLOCK`；
- `Depth: 0/1/infinity` 的上限、重复 ID 和客户端断开行为；
- 单范围 `Range`、`If-Range`、`Content-Range` 和 `416`；
- Basic Auth、同源写入检查和错误响应；
- 多 WPS 空间的虚拟文件夹路由；
- Cookie/CSRF 文件权限、refresh 后的原子更新和日志脱敏；
- 上传并发、缓存、临时文件和磁盘空间保护。

WPS 私有请求的字段和签名 URL 只能按当前已确认的行为实现。迁移语言不能成为猜测新 WPS 接口的理由。

## 8. 分阶段迁移计划

### 阶段 A：测量和冻结契约

1. 为当前 Python 服务补充吞吐、内存、并发和断开连接基准。
2. 将现有测试整理为与语言无关的 HTTP/WebDAV 黑盒测试。
3. 固定响应状态码、头部、错误格式和多空间路径规则。
4. 记录 Python 版本作为可回滚基线。

### 阶段 B：拆分前端

1. 把内嵌 HTML、CSS 和 JavaScript 拆为 `web/` 静态文件。
2. Python 后端先继续提供这些文件，确保用户界面行为不变。
3. 在桌面和移动视口验证上传、拖动、错误状态和空间文件夹显示。
4. 只在前端验收通过后再切换后端语言。

### 阶段 C：实现 Go 只读路径

1. 先实现健康检查、Basic Auth、静态文件、目录列表和元数据。
2. 用同一组黑盒测试对比 Python 和 Go 响应。
3. 加入 WPS 请求超时、响应大小限制、路径校验和日志脱敏。
4. 暂不实现写操作，避免同时排查太多问题。

### 阶段 D：实现流式传输和写操作

按风险从低到高迁移：下载、单范围下载、普通上传、multipart 上传、文件夹创建、重命名/移动、删除、COPY、锁。每完成一个能力，都要通过 Python/Go 对照测试和专用 WPS 测试目录验收。

### 阶段 E：灰度和切换

1. Go 服务使用不同本地端口运行，Python 服务继续作为回滚版本。
2. 先只允许本人账号和测试目录访问 Go 服务。
3. 观察至少一个完整的 Cookie refresh、上传失败重试和客户端断开周期。
4. 切换 systemd/Docker 启动目标，保留旧二进制和配置以便快速回滚。
5. 稳定后再删除旧运行时，不删除用户的 secret 和工作区文件。

## 9. 失败和回滚标准

出现以下任一情况，停止扩大迁移范围并回滚：

- 文件内容校验不一致；
- WebDAV 客户端看到错误的目录层级、空间或文件名；
- 上游 Cookie、CSRF 或签名 URL 出现在日志中；
- 客户端断开后仍持续占用 WPS 请求或临时文件；
- 内存峰值高于 Python 基线或触发 VPS OOM；
- Range 响应没有严格匹配请求范围；
- 失败上传留下无法清理的临时文件或远端对象；
- 安装器需要用户执行额外的编译、包管理或手工配置步骤。

回滚应只需要切换服务程序/镜像和启动配置，不应要求用户重新登录 WPS。Cookie、CSRF、Basic Auth 和工作区文件必须继续使用原路径和权限。

## 10. 部署策略

最终目标是给用户提供与当前相同的两条一键安装路径：

- Native：下载并运行一个经过校验的 Go 二进制和静态资源；
- Docker：使用包含 Go 编译产物的最小运行时镜像。

用户不需要安装 Go、C++ 编译器、Python 包管理器或前端构建工具。开发者可以在 CI 中完成编译、跨平台构建、单元测试、黑盒测试和发布清单生成。

Native 与 Docker 必须继续支持常见 Linux 发行版、自定义端口、当前用户运行和无域名 HTTP 场景；HTTPS 仍建议交给反向代理处理。

## 11. 暂不做的事情

- 不在没有基准数据时宣称 Python 一定是瓶颈；
- 不同时迁移登录助手、服务端和前端所有代码；
- 不为了追求性能引入复杂的微服务或本地数据库；
- 不把 WPS Cookie、refresh token 或签名 URL 放进测试样本；
- 不直接用 C++ 重写后跳过协议对照测试和安全审计；
- 不改变用户当前的安装、登录和空间选择步骤。

## 12. 验收清单

- [ ] Python 基线性能和资源数据已记录。
- [ ] HTML/CSS/JavaScript 拆分后功能和安全编码一致。
- [ ] Go 只读接口通过全部跨语言黑盒测试。
- [ ] 多空间虚拟文件夹与旧单空间配置均可用。
- [ ] 上传、下载、Range、COPY、锁和 Depth 行为一致。
- [ ] Cookie refresh 和原子凭据更新通过测试。
- [ ] 客户端断开会释放上游连接和本地资源。
- [ ] Native/Docker 安装无需用户安装编译环境。
- [ ] 旧 Python 版本可在一次服务重启内恢复。
- [ ] README 和升级/回滚文档已同步。

## 最终建议

先用基准确认 Python 的实际瓶颈，然后拆分原生前端，再以 Go 实现兼容后端。C++ 可以作为未来的高性能实现或独立实验分支，但不应作为第一版迁移的默认选择。这样既能获得单二进制、低内存和高并发收益，也能把用户的安装和登录步骤保持在当前水平。
